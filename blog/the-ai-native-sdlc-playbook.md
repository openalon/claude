# AI 原生 SDLC 实践手册

[阅读 Claude Blog 原文：The AI-Native SDLC playbook](https://claude.com/blog/the-ai-native-sdlc-playbook)

> 本文是对官方文章的中文学习整理，不是官方翻译。官方内容、我的理解和实践记录分别标注。

## 先说结论

官方文章的核心判断是：当 AI 能快速生成代码后，软件交付的主要瓶颈会从“写代码”转移到需求澄清、设计、测试、审查、发布和维护。组织需要把 SDLC 重新设计为一个由 AI 参与、由版本化工件衔接、并且持续循环的开发系统。

这并不意味着取消人工责任，而是把人工判断集中到意图、风险、政策例外和生产发布等关键节点。

## 它解决什么问题

传统 SDLC 中的审批、交接和审查机制，大多围绕人工编写代码的速度建立。当代理能够并行完成大量实现工作时，原本合理的流程可能反而变成新的排队点：需求还没有被结构化，测试和审查跟不上，部署与维护也无法吸收更快的变更速度。

文章提出的 AI-native SDLC，试图解决三个连接问题：

- 如何让需求意图在后续阶段不丢失；
- 如何让组织约定、安全规则和领域知识被 AI 稳定复用；
- 如何让测试、发布和生产事件重新反馈到开发循环中。

## 关键机制

### 1. 用版本化工件连接各阶段

文章将 SDLC 描绘成循环，而不是单向流水线。每个阶段都产出可提交、可追踪、可被下一阶段读取的工件，形成审计链。文中列出的典型工件包括：

- `intent.md`：记录需求背景、目标和意图；
- `spec.md`：把需求转化为可执行的规格；
- `plan.md`：说明实现步骤和验证方式；
- 代码变更、测试结果和审查结果；
- 部署记录、监控事件和后续维护记录。

如果组织仍保留旧系统，文章建议为每类工件明确唯一事实来源，并用记录编号、提交哈希或链接把新旧系统关联起来。

### 2. Plan：先捕获意图

第一阶段不是立即生成代码，而是用 `intent.md` 把问题、目标和期望结果固定下来。这样做的价值在于，后续规格、计划和实现都有可回看的依据，也能减少代理只根据一句模糊需求开始编码的情况。

### 3. Design：把意图转成规格

设计阶段通过组织技能和领域规则，把意图转化为 `spec.md`。这里的重点不是让 AI 自由发挥，而是让它能够读取组织已有的 API 约定、安全要求、架构限制和业务知识。

### 4. Build：让代理在受控上下文中实现

文章提到的实现支撑包括：

- 计划模式：先分析和拆解任务，再执行修改；
- `CLAUDE.md`：保存代码库约定、命令、架构和常见错误；
- Skills：把安全、合规、品牌和 API 等政策转化为可复用指令；
- Hooks：对敏感操作施加确定性的允许、询问或阻止；
- 并行会话：在适合的任务上提升吞吐量。

这些机制共同构成代理的工作边界：哪些知识应该被读取，哪些操作可以自动完成，哪些操作必须经过确认。

### 5. Test：把反馈循环前移

代理应在人工审查前运行测试、构建、静态检查或视觉验证。测试不只是验证业务代码，也应该持续评估代理配置本身是否仍然有效。

文章强调，测试阶段的意义在于快速形成反馈，而不是把质量检查全部推迟到合并或发布之前。

### 6. Deploy：自动化不等于取消生产控制

代理可以负责准备发布、执行检查和完成低风险操作，但生产发布仍应保留分支保护、代码所有者或发布负责人的审批。这样既能利用自动化速度，也能在高影响操作上保留明确责任边界。

### 7. Maintain：让生产信号回到开发循环

监控指标、事件、工单、聊天消息和定期安全扫描，都可以触发新的诊断、PR 或 `intent.md`。确定性的阈值和触发条件由脚本及版本化配置负责，模型则在权限范围内进行诊断或提出变更建议。

## 适合谁

这套方法尤其适合：

- 已经在团队中使用 Claude Code 或其他编码代理的工程组织；
- 需要把 AI 产出接入现有审查、CI/CD 和合规流程的团队；
- 有较多遗留系统，需要同时维持旧流程与新工件链路的组织；
- 希望衡量 AI 对完整交付流程影响，而不仅是统计生成了多少代码的团队。

## 我的理解

我认为文章最重要的转变，是把“AI 辅助写代码”提升为“AI 参与软件交付系统设计”。如果只增加一个代码生成工具，而不调整需求、知识、测试、审批和维护的连接方式，团队很容易只是把瓶颈从编辑器转移到审查队列。

其中，版本化工件是一个很实用的抽象。它让代理的工作不再只是一次性的对话输出，而是可以被后续阶段读取、被团队复盘、被审计链追踪的中间结果。

另一个关键点是“确定性控制与模型判断分工”：脚本和 Hooks 负责边界，模型负责解释、诊断和提出方案。这比单纯依赖模型自觉遵守规则更适合生产环境。

## 实践记录

> 尚未在真实团队或生产系统中完整实践本文提出的 AI-native SDLC，以下内容待验证。

可先在一个小型项目中验证以下闭环：

1. 为一个真实需求创建 `intent.md`；
2. 让代理生成并审阅 `spec.md` 与 `plan.md`；
3. 在 `CLAUDE.md` 中补充项目约定，并用测试、构建和静态检查验证实现；
4. 记录审查结果和发布审批；
5. 观察一次测试失败或线上事件能否形成新的维护任务；
6. 对比采用前后的需求澄清时间、返工次数、审查周期和缺陷逃逸率。

文章建议关注的衡量指标包括：意图到规格的耗时、计划到合并的时间、返工次数、测试通过率、审查周期、缺陷逃逸率和事件修复率。这些指标也比单独统计代码行数更能反映流程是否真正变快、变稳。
